Concrètement, à chaque modification touchant une zone du fichier : vérifier qu'aucune fonction/composant/état devenu inutilisé n'y traîne, et mutualiser toute logique ou tout style dupliqué à l'identique (ou quasi) à plusieurs endroits plutôt que de laisser une nouvelle copie s'ajouter aux précédentes. ## 1. Objectif & format

Tracker Pokédex personnel — React 18 + Babel via CDN dans un unique `index.html` autonome (aucun build, aucune install), hébergé sur GitHub Pages, utilisable PC + mobile (Samsung Galaxy/Samsung Internet). Remplace un ancien classeur Excel complexe. La documentation (ce fichier) est **séparée** du HTML — elle a été intégrée une fois (constante `DOC_CONTENT`) puis retirée sur demande explicite car ça alourdissait trop `index.html`. Ne jamais la réintégrer sans demande explicite.

**Structure du fichier** (dans l'ordre) : `<script>` définissant `window.storage` → CDN React/ReactDOM/Babel/XLSX → `<script>` classique définissant `window.DATA = {...}` (bloc JSON pur, aucune JSX — voir §2) → `<script type="text/babel" data-presets="react">` avec tout le code de l'app (démarre par `const DATA = window.DATA;`). Cette dernière séparation existe uniquement pour alléger la validation JSX à chaque édition (le bloc `DATA` fait ~1 Mo à lui seul et n'a besoin d'aucune transpilation Babel) — sans aucun impact sur le comportement de l'app. Pour ajouter un jeu : la table Pokédex va dans le bloc `window.DATA`, tout le reste (`GAME_ORDER`, `JEU_VIDEO_DEFS`, filtres...) dans le bloc Babel comme d'habitude.

## 2. Stockage

- **`window.storage`** : wrapper autour de `localStorage` (préfixe de clé `"pkdx_"`), défini en tout début de fichier, dans un `<script>` séparé du reste. Fonctionne dans n'importe quel navigateur, rien à voir avec l'environnement Claude. `get(key)` retourne `{ value: null }` pour une clé absente (jamais d'exception) — comportement corrigé, voir §6 pour le piège que l'ancien comportement (levait une exception) provoquait systématiquement sur tout bloc lecture+écriture dans le même `try`.
- **`DATA`** (alias de `window.DATA`, voir §1) : bloc JSON unique embarqué, **purement structurel** (disponibilité par jeu, sprites, positions de boîtes, capacités Alpha, mapping d'évolution, capacité Jeu vidéo) — **ne contient plus aucune capture réelle**. Toute donnée de possession vit exclusivement dans `window.storage`, restaurée par import `.json`/Excel ou saisie directe.
- **Clés `ALL_KEYS`** (exportées/importées/effacées ensemble) : `caught_<jeu>` (un par code `GAME_ORDER`), `go1_pokedex_forms`/`go1_shiny_forms` (Jeu Go 1, toutes formes), `go1_pokedex_unique`/`go1_shiny_unique`/`go1_chanceux`/`go1_parfait`/`go1_purifie`/`go1_obscur`/`go1_xxs`/`go1_xxl` (Go 1, forme unique), `shiny_catches`, `double_catches`, `manual_caught`, `alpha_caught`, `custom_marques`, `custom_modes`, `custom_locations`, `custom_jeux`, `custom_details`, `mode_marques`/`detail_marques`, `custom_events`, `custom_interjeu`, `catalog_overrides`, `catalog_additions`, `catalog_deletions`, `box_settings` (ancien réglage par marque, conservé en lecture seule pour migration, voir "Réglages de boîte par vue" §5ter), `game_view_box_settings` (réglage courant, par vue — même paragraphe), `box_group_overrides`, `custom_box_groups`, `game_jeu_overrides`, `game_tab_sources`, `custom_jeu_views`, `game_view_number_overrides`, `game_view_box_group_overrides` (les 4 dernières : voir §5ter "Vues Jeu"), `custom_jeu_video_defs`/`custom_jeu_video_groups`/`custom_jeu_video_gens` (Jeu vidéo personnalisable — jeux, regroupement paire/triple, blocs de génération, § voir §4), `home2`, `home2_search_suffix`, `go2`, `go2_search_suffix`, `parfait_search_suffix` (§5quater/§5quinquies/§5bis), `evolution_chain_overrides` (§5sexies).
- **`custom_marques` auto-complétée** : à chaque chargement (`useCustomLists`, et redondant dans `SettingsView.loadAll` au cas où Paramètres soit ouvert en premier), toute marque de `GAME_ORDER` absente de `custom_marques` y est automatiquement ajoutée puis persistée — sinon une marque nouvellement créée par code (ex. GBA/VV, voir §5ter) resterait invisible dans les champs "Marque" de Shiny/Double/Event/Interjeu (alimentés par `custom_marques` + valeurs découvertes dans les captures existantes, jamais par `GAME_ORDER` directement) tant qu'elle n'y est pas ajoutée manuellement via Paramètres.
- **Métadonnées locales hors `ALL_KEYS`** (jamais exportées/synchronisées) : `last_export_at`, `pkdx_mod_count` (compteur de modifs depuis le dernier export — alimente le point orange/vert à côté du logo), `pkdx_gist_mod_count`, `pkdx_gist_token`/`pkdx_gist_id`/`pkdx_gist_synced_at` (en `localStorage` brut, hors `window.storage`), `jeu_options_migrated` (flag de migration ponctuelle, § voir "Jeu-DO" plus bas).

### Structure `DATA.nat[i]` (tableau positionnel, pas d'objet)

```
[0]  nat        — numéro national (parfois string "E-1"/"I-29", ou float 0.1/0.5 pour Zygarde)
[1]  nom
[2]  forme      — null si forme normale ; parfois un nombre (Zygarde) → toujours caster String() avant .trim()/concat
[3]  region
[4]  lien       — URL Poképédia
[5]  caughtAny  — TOUJOURS 0 dans DATA (ownership vidée, voir plus haut)
[6]  shinyAny   — idem
[7]  avail[]    — dispo par jeu, indexé selon DATA.natGames — STRUCTUREL, fiable
[8]  caughtGame[] / [9] shinyGame[] — TOUJOURS 0
[10] genericCaught / [11] genericShiny — TOUJOURS 0 (pseudo-jeu "Forme")
[12] alphaCaughtLA / [13] alphaCaughtLZA — scalaires 0/1, TOUJOURS 0
[14] famille    — numéro de ligne d'évolution, nombre ou null — structurel, fiable, éditable en fiche
```
Chaque ligne porte aussi en mémoire (jamais dans le JSON figé) `row.__baseKey` (clé nom|forme d'origine, lignes structurelles) et `row.__additionId` (lignes créées via `catalog_additions`).

**Autres clés top-level de `DATA`** : `games` (par jeu, structure similaire), `boxGroups`, `boxPrefixDefault`, `sprites`, `spriteVariants`, `shinyCatalog` (structurel, jamais vidé), `shinyCatches` (vide par défaut), `nat`, `natGames`, `gameIndex`, `alphaCapable`, `evolutionMode`, `doubleCatches`, `eventCatalog`, `interjeuCatalog`, `homeDex` (Pokédex Home, booléen par clé), **`jeuVideo`** (nouveau — voir §5). Calculés en mémoire : `natSortOrder`, `__additionIdxById`.

**⚠️ Règle absolue** : ne jamais lire une valeur d'ownership (`r[5]`/`r[6]`/`r[8]`-`[13]`, `DATA.games[...][3]`) comme une vérité — toujours passer par `window.storage`/hooks dédiés (`useCollection`, `useLiveNat`, `useShinyCatches`, `useDoubleCatches`). Les champs structurels (`avail[]`, régions, sprites, capacités, `homeDex`, `jeuVideo`) restent en revanche fiables directement depuis `DATA`.

Clé de correspondance nom+forme dans tout le projet : toujours `nom + "|" + (forme || "")`, `forme` casté en `String()` avant toute méthode de chaîne (Zygarde a une forme numérique).

## 3. Catalogue Pokémon (Paramètres → icône ✎ / crayon)

Édition centralisée via `CatalogEntryModal` (partagé par `CatalogQuickEditButton` et `CatalogEditor`). Champs : Nom, Forme, **Numéro national + Région sur la même ligne**, **Méthode d'évolution** (libellé court, ex-"Évolution (ex. ...)"), **Famille (numéro de ligne d'évolution)** (libellé court, sans référence Excel), capacité Alpha LA/LZA, pilules **Méga/Gmax/Gmax gène** (§4), Pokédex Home, Marques possibles, **Numéro spécifique par jeu**, **Numéro spécifique par jeu vidéo** (§4, distinct du précédent — un numéro par paire/triple `JEU_VIDEO_PAIRS`, pas par marque) et **Jeu vidéo** (sections indépendantes, chacune repliable/dépliable, **repliées par défaut** à l'ouverture de la fiche).

- **Clé stable** : `catalog_overrides["nom|forme d'origine"]` pour les fiches déjà existantes (clé = `row.__baseKey`, jamais positionnelle) ; `catalog_additions[]` (par `id`) pour les Pokémon entièrement nouveaux. `persistCatalogEdit(idx, d)` route automatiquement vers l'un ou l'autre.
- **Suppression** (`catalog_deletions`) : ne touche jamais aux captures déjà enregistrées, réversible depuis Paramètres.
- Le crayon (`CatalogQuickEditButton`) n'apparaît que sur les pages de détail (Shiny, National, Home/jeux), jamais sur une liste. **Icône seule partout** (plus de prop `label`, ni de style `corner` — alignement complet, § demande explicite : National avait initialement gardé un libellé "Modifier", retiré ensuite pour cohérence avec les 3 autres fiches). Placé dans la **barre du bas** de chaque fiche modale (slot `center` de `FloatingCardNav`, §5septies), jamais sur la ligne du nom — voir §5ter "Fiche de capture (jeux/marques)" et §5septies pour le détail de la présentation.
- **`CatalogEntryModal` elle-même harmonisée avec les autres fiches** (§ demande explicite, "on va plus loin dans l'harmonisation") : plus de titre texte ("Ajouter un Pokémon"/"Modifier Pokémon") — un simple **+** en médaillon pour une création, et l'artwork encadré `FicheArtworkBlock` pour une modification (numéro en médaillon **affiché mais non éditable** ici — contrairement à `BoxGroupModal`/`JeuMultiSourceModal`, §5ter — l'édition reste le champ "Numéro national" du formulaire, qui accepte des préfixes du type "E-219" incompatibles avec la limite 4 caractères du badge). Le lien Poképédia est désormais une pilule (bordure `ACCENT`, même style que `FicheNameRow`) accolée au champ Nom, plutôt qu'un lien texte centré sous l'artwork. **Supprimer/Annuler/Enregistrer** ont quitté le panneau pour le slot `center` de `FloatingCardNav` (barre du bas, §5septies), en icônes seules (🗑 rouge/×/`SaveButton` — voir §5septies "Barre du bas" pour l'indicateur de modifications non enregistrées) — même mécanisme que les autres fiches bien que `CatalogEntryModal` n'ait pas de navigation précédent/suivant (`hasPrev`/`hasNext` toujours `false` ; le composant reste affiché grâce au `center` fourni, §5septies "Navigation entre fiches"). La petite fenêtre de confirmation de suppression reste séparée, par-dessus, inchangée.

## 4. Jeu-DO vs Jeu vidéo — bien distinguer ces deux concepts

**Jeu-DO** (Dresseur d'Origine) : à quel jeu précis un **exemplaire capturé** appartient (ex. "Écarlate - 139868"). Champ par capture, existe sur Shiny (`rec.jeu`), Double (`rec.jeu`), Interjeu (`it.jeu`), Event (`e.jeuDO`, uniquement si `e.doPerso` coché — "DO personnel", distinct du champ libre `e.do` = nom du dresseur), par Pokémon dans les onglets jeu (`game_jeu_overrides[jeu]["nom|forme"]`), et par espèce dans Go 1 (§5bis, `go1_pokedex_unique`/`go1_shiny_unique`...). Filtre "Jeu - DO" présent sur **tous les onglets sauf National** (qui a son propre filtre "Jeu", de sens différent — disponibilité structurelle), avec une option **"Jeu non indiqué"** (`__none__`) partout, y compris les onglets jeu du menu Home (manquait avant, ajouté par cohérence).

- **Règle d'architecture (cause d'un bug sérieux, ne jamais y revenir)** : les valeurs possibles d'un Jeu-DO viennent **uniquement** de `custom_jeux` (ajouts utilisateur via **+**) ou de valeurs **découvertes** dans les captures existantes (`orderedList(customJeux[marque], discovered)`) — **jamais** d'une table figée séparée. Une ancienne table `JEU_OPTIONS_BY_MARQUE` (importée une fois de l'Excel) violait cette règle et causait un bug de duplication auto-amplifiante (le glisser-déposer de Paramètres réécrivait le doublon à chaque réorganisation). Elle a été **entièrement retirée** ; son contenu a été fusionné une seule fois dans `custom_jeux` au premier chargement après le fix (`jeu_options_migrated`).
- Renommer une valeur de Jeu-DO dans Paramètres cascade vers **5 endroits** : Shiny, Double, `game_jeu_overrides` (onglets jeu), Event (`jeuDO`), Interjeu (`jeu`) — vérifier que `cascadeRename` couvre bien les 5 avant toute nouvelle modification de ce mécanisme.

**Jeu vidéo** (nouveau, bloc catalogue distinct de "Marques possibles") : dans quel(s) **jeu(x) précis** au sein d'une marque un Pokémon est **disponible** (structurel, pas une capture) — ex. distinguer Écarlate/Violet, tous deux marque Paldea. Stocké dans `DATA.jeuVideo["nom|forme"] = { <clé>: true/false, ... }`, édité via `catalog_overrides`/`catalog_additions` (champ `jeuVideo`, objet fusionné, jamais écrasé entièrement). Défini par `JEU_VIDEO_DEFS`, rangé par génération dans la fiche catalogue — **liste de départ** (avant toute édition, § voir "Jeu vidéo personnalisable" ci-dessous, qui décrit l'état réellement à jour) :

```
1G-2G   : Rouge, Bleu, Jaune, Or, Argent, Cristal
3G      : Rubis, Saphir, Émeraude, Rouge Feu, Vert Feuille
4G      : Diamant, Perle, Platine, Or HeartGold, Argent SoulSilver
5G      : Noir, Blanc, Noir 2, Blanc 2
6G      : X, Y, Saphir Alpha, Rubis Oméga
7G      : Soleil, Lune, Ultra-Soleil, Ultra-Lune
Let's Go : Let's Go Pikachu, Let's Go Évoli
8G      : Bouclier, Épée
Legends : Arceus, Z-A
9G      : Écarlate, Violet
GBA     : Rouge Feu Switch, Vert Feuille Switch (marque GBA, § voir §5ter)
10G     : Vents, Vagues (marque VV, § voir §5ter)
Autre   : Go sorti (clé "go"), Go (clé "goattrapable")
```
Helpers : `jeuVideoFor(nom, forme)` (objet complet), `goSortiFor(nom, forme)` (raccourci `.go`, disponibilité générale dans Pokémon GO), `goAttrapableFor(nom, forme)` (raccourci `.goattrapable`). **"Go" (attrapable) vs "Go sorti"** : "Go sorti" = le Pokémon est sorti dans Pokémon GO en général (filtre "Sorti" de l'onglet Go/Go 1, comme avant) ; "Go" = **cette forme précise** est attrapable telle quelle dans Pokémon GO, indépendamment de son appartenance à la marque Go/Pokédex Home (ex. Palkia Originel, attrapable en Go mais non transférable sur Home) — même logique que les formes dominantes Alola (`jeuOnlyFormsFor`, §5ter) : `go1AllFormsSorted` (§5bis) inclut ainsi, en plus des formes réellement membres de `DATA.games["Go"]`, celles marquées `goattrapable` seules (mémoïsées au niveau module, `go1AttrapableOnlyForms`, pour ne jamais rebalayer tout le Pokédex à chaque espèce). Affichées **côte à côte, "Go" à gauche de "Go sorti"** (même paire `JEU_VIDEO_PAIRS`) partout où ces pilules apparaissent : bloc catalogue "Jeu vidéo", "Disponible dans" des fiches Home/Home + jeu de la marque Go (`allMarqueGames`, §5ter — insertion faite au niveau du calcul, jamais en réécrivant une vue déjà créée par l'utilisateur), et fiche Go 1 (`Go1SpeciesModal`, §5bis). Sert aussi à filtrer la liste des vues Jeu précises (§5ter — la pilule "Home" des fiches de capture n'utilise PAS ce mécanisme, voir §5ter pour la distinction).

### Jeu vidéo personnalisable (Paramètres → "Jeu vidéo")

`JEU_VIDEO_DEFS` (jeux précis), `JEU_VIDEO_PAIRS` (regroupement paire/triple à numéro partagé) et `JEU_VIDEO_GENS` (ordre des blocs de génération) sont **entièrement personnalisables** (§ demande explicite : "éditer les jeux vidéo... changer paire/triple... rajouter des blocs... indiquer dans quelles marques il sont"), pas seulement les valeurs de disponibilité qu'ils définissent. Stockage : `custom_jeu_video_defs` (`[{ key, label, gen, marques: [...] }, ...]`), `custom_jeu_video_groups` (`[{ keys: [...], acronym }, ...]`), `custom_jeu_video_gens` (`[...]`, ordre d'affichage).

- **Rétroactivité** (§ demande explicite, garantie) : `DEFAULT_JEU_VIDEO_DEFS`/`DEFAULT_JEU_VIDEO_GROUPS`/`DEFAULT_JEU_VIDEO_GENS` (constantes module-level, contenu = l'ancienne liste fixe ci-dessus) ne sont qu'une **graine de migration one-shot**, même principe que `DEFAULT_JEU_VIEWS` → `custom_jeu_views` (§5ter) : au tout premier chargement (aucune des 3 clés storage encore écrite), `applyJeuVideoCustomizations()` les copie telles quelles dans le storage — mêmes clés, mêmes regroupements, mêmes générations qu'avant cette fonctionnalité, aucune donnée existante (`DATA.jeuVideo`/`DATA.jeuVideoNumbers`, colonnes Excel `JV_<clé>`) ne change de sens. Une fois ces 3 clés écrites, elles seules font foi — les constantes `DEFAULT_*` ne sont plus jamais relues.
- **Liaisons vivantes** : `JEU_VIDEO_DEFS`/`JEU_VIDEO_PAIRS`/`JEU_VIDEO_GENS` sont déclarées `let` (pas `const`) et **réaffectées** par `applyJeuVideoCustomizations()` juste avant le tout premier rendu (bootstrap en fin de fichier, avant `applyCatalogCustomizations()`) — le reste du code (Catalogue, export National, pilules, filtres) continue de les lire tel quel, qu'elles viennent de la graine par défaut ou du storage personnalisé. `SettingsView` les **réaffecte aussi directement** à chaque édition (`applyJvDefs`/`applyJvGroups`/`applyJvGens`), en plus de persister le storage — pas besoin de recharger la page pour que le reste de l'app reflète un changement.
- **Marques par jeu** (`def.marques`, § demande explicite) : tableau de codes `GAME_ORDER` où ce jeu précis se range (ex. `["VI"]` pour Saphir Alpha). Purement informatif/organisationnel pour l'instant — n'est lu par aucune autre logique de l'app (ne pilote ni `custom_jeu_views` ni l'affichage des pilules "Disponible dans", §5ter).
- **Acronyme par groupe** (`grp.acronym`) : nom court utilisé dans les en-têtes Excel National "No_<ACRONYME>" (§7). Un nouveau groupe (nouveau jeu ajouté, ou jeu détaché d'un groupe existant) reçoit un acronyme par défaut calculé depuis les libellés (`defaultJeuVideoGroupAcronym` — initiale de chaque mot, accents retirés, ex. "Saphir Alpha"+"Rubis Oméga" → "SARO") ; librement modifiable ensuite, jamais recalculé après coup.
- **Regroupement paire/triple** : un groupe = un ou plusieurs jeux partageant le même numéro spécifique (voir "Numéro spécifique par jeu vidéo" ci-dessous). Plus de flag `sharedNumber` (ancien mécanisme) : Arceus/Z-A sont désormais deux groupes à un seul jeu chacun (un groupe à un seul jeu partage trivialement son numéro avec lui-même) — Yann peut les fusionner en un vrai groupe partagé depuis Paramètres s'il le souhaite. Édition (Paramètres → "Jeu vidéo", par bloc de génération) : retirer un jeu de son groupe (✕, redevient seul) ou le fusionner dans un autre groupe (menu déroulant "+ fusionner un jeu ici", limité aux jeux **absents** de ce groupe) — aucune limite sur les jeux fusionnables entre générations différentes, non bloqué par l'UI (cas non prévu par le jeu réel, laissé à la discrétion de Yann).
- **Marques (menu déroulant)** : cochées via `MultiPicker` (§ demande explicite, "menu déroulant comme pour les générations" plutôt que des pastilles) — sur la **même ligne** que le nom du jeu et le sélecteur de génération.
- **Ajouter un jeu** (par bloc de génération) : clé générée depuis le libellé saisi (translittéré, minuscule, sans accents ni espaces), garantie unique (suffixe numérique si collision) — crée aussi son propre groupe à un seul jeu.
- **Ajouter un bloc de génération** : ajoute une entrée vide à `JEU_VIDEO_GENS`, sans jeu dedans pour l'instant — apparaît immédiatement comme section disponible pour "Ajouter un jeu".
- Import Excel (feuilles "Jeu vidéo"/"Générations JV", §7) applique les mêmes règles de fusion (présence de colonne = donnée touchée) — jamais de suppression de jeu via cette voie.

### Numéro spécifique par jeu vidéo (bloc catalogue, distinct de la vue Jeu §5ter)

Un **numéro par paire/triple** `JEU_VIDEO_PAIRS` (ex. un numéro Saphir Alpha/Rubis Oméga, distinct du numéro national et du numéro "Numéro spécifique par jeu" par marque) — stocké dans `DATA.jeuVideoNumbers["nom|forme"] = { <pairKey ou clé du jeu si groupe à un seul jeu>: "numéro", ... }`, édité via `catalog_overrides`/`catalog_additions` (champ `jeuVideoNumbers`, objet fusionné). Édition dans la fiche Catalogue (§3), une ligne par groupe, rangée par génération, libellé = jeux du groupe concaténés ("Saphir Alpha / Rubis Oméga").

**Entièrement indépendant de `custom_jeu_views`/`game_view_number_overrides`** (§5ter — Vues Jeu, numéro par vue utilisé pour le **tri et le nommage des boîtes** d'une vue précise) : ce champ ne pilote ni le tri ni le nommage de boîte de quoi que ce soit, c'est une information de référence pure, toujours disponible quelle que soit la vue configurée (ou non) pour la marque concernée — c'est ce champ, et non `game_view_number_overrides`, qui alimente les colonnes "No_<ACRONYME>" de l'export Excel National (§7).

### Note de disponibilité conditionnelle (texte libre)

Une valeur `jv[clé]` n'est plus limitée à `true`/`false`/non renseigné : une **chaîne de texte non vide** (ex. `"9G+"`) est acceptée — cas typique : une espèce est attrapable dans un jeu donné (ex. Insolourdo en Cristal) mais son évolution ne peut être obtenue que dans un jeu ultérieur (ex. Deusolourdo, disponible seulement à partir d'Écarlate/Violet). La note se saisit dans le même champ texte que la case à cocher correspondante (fiche Catalogue, bloc "Jeu vidéo") : remplie, elle remplace le booléen ; vidée, on retombe sur l'état de la case.

- `isJvTextNote(v)` détecte une note texte. `jvAvailable(v)` (= `v === true || v === undefined`) est la fonction à utiliser pour tout test **d'inclusion dans une vue précise** (`rowsForPair`, `pairStatsFor`, filtre "Disponibilité" §5ter) — une note texte y compte comme **indisponible**, jamais comme disponible, même si elle reste "truthy" en JS. Ne pas confondre avec un simple test de troncature (`jv[k]`), qui traiterait par erreur la note comme disponible.
- `jeuOnlyFormsFor` (§5ter) reste inchangé : il exige déjà `=== true` strict, donc une note texte n'y déclenche jamais d'inclusion hors-marque.
- Excel : colonnes `JV_<clé>` de la feuille "National" (§7) — `0`/`1` classiques ou texte libre, préservé tel quel à l'import/export (`parseJvCell`/`isJvTextNote`).
- Affichage : `AvailabilityPills` montre la note en suffixe du bouton (ex. "Cristal (9G+)"), pilule visuellement **éteinte** (comme indisponible) — cliquer dessus la remplace par un simple booléen (bascule binaire, la note n'est éditable qu'en Catalogue).

### Pilules "Méga"/"Gmax"/"Gmax gène" (bloc catalogue "Pokédex Home & Alpha")

Marquage **structurel et purement manuel** — distinct de la détection par texte de forme (`isMegaOrGmaxForme`/`dynamaxInfoFor`, §5sexies/§5) : trois pilules à côté d'Alpha LA/LZA et Pokédex Home, stockées dans `DATA.formTags["nom|forme"] = { mega, gmax, gmaxGene }`, éditées via `catalog_overrides`/`catalog_additions` (champs `formMega`/`formGmax`/`formGmaxGene`, même schéma que `alphaLA`/`alphaLZA`). Lues via `formTagsFor(nom, forme)` — **reflète uniquement le tag stocké, jamais une déduction depuis le texte de forme** (une fusion avec la détection automatique a été essayée puis retirée sur demande explicite : ces pilules doivent rester une valeur que l'utilisateur ajoute lui-même). "Gmax gène" = le Pokémon porte le gène Gigamax mais ne peut pas (encore) Gigamaxer lui-même (ex. Crèmy, Chapotus) — mutuellement exclusive avec "Gmax" dans la fiche catalogue (cocher l'une décoche l'autre) ; "Méga" reste indépendante.

Tous les usages suivants restent branchés sur `formTagsFor` telle quelle (aucune détection automatique nulle part, y compris dans ces usages) :
- **Filtre Dynamax** (onglets jeu, National, Shiny, Double, Event) : `dynamaxValueFor(nom, forme)` fait passer "Gmax gène" (`formTagsFor(...).gmaxGene`) **avant** la détection par texte (`dynamaxInfoFor`) — une forme dont le libellé contient "Gmax gène" (ex. Crèmy) matcherait sinon à tort "Gmax" simple via `dynamaxInfoFor`. Options du filtre Dynamax : Gmax / Non Gmax / Gmax gène (cette dernière n'apparaît que si au moins une forme de la marque affichée la porte, `hasGmaxGeneForms`, sauf sur National/Shiny/Event où le filtre est déjà affiché sans condition). Le filtre **Taille** (Alpha/Normal, LA/LZA uniquement) n'a plus aucun lien avec Gmax gène — distinction corrigée après une première tentative qui l'y avait placée à tort.
- **Filtre Méga** (National uniquement, dédié, indépendant de Dynamax qui ne couvre que Gmax) : `matchesMegaRow`/`formTagsFor(...).mega`.
- **Go 1, modes "Méga"/"Gmax"** (§5bis) : `NAT_ALL_FORMS` filtré sur `formTagsFor(...).mega`/`.gmax` — tout le Pokédex, pas seulement les formes de la marque Go (une forme peut être taguée sans être elle-même attrapable dans Pokémon GO).
- **Export Excel National** (§7) : colonnes `FormMega`/`FormGmax`/`FormGmaxGene`.

Plus d'onglet "Jeu" séparé (`JeuNavSelect`/`JeuGameView`/`JEU_ORDER` supprimés, § demande explicite). Go 1 vit désormais **dans l'onglet Home de la marque Go**, accessible via le **même bouton flottant "Mode"** que Home/Home + jeu/vues précises des autres marques (§5ter) — pas de bascule séparée en haut de page. Composant dédié (`Go1View`, ne réutilise pas `GameView` par ailleurs) : pas de vue Boîte, pas de région/groupe de boîte en liste.

Pokédex/Shiny ont une sous-vue **Toutes formes** (une ligne par forme, clé `nom|forme`) / **Forme unique** (une ligne par espèce, clé = numéro national) — bascule dans le menu Affichage, avec Liste/Grille (grille : groupée par région, 4 colonnes par défaut, réglable). Chanceux/Parfait/Purifié/Obscur/XXS/XXL n'existent qu'en forme unique. **Méga/Gmax** (`GO1_FORM_ONLY_MODES`) restent **toujours en forme** (jamais de bascule vers "Forme unique" — seule une forme précise peut être Méga/Gmax, pas l'espèce dans son ensemble) et ne listent **que** les formes portant la pilule structurelle correspondante (`formTagsFor(...).mega`/`.gmax`, §4) — source = **tout le Pokédex** (`NAT_ALL_FORMS`), pas seulement les formes de la marque Go (`allForms`) : une forme peut être taguée Méga/Gmax sans être elle-même attrapable dans Pokémon GO. Simple suivi de possession (stockage dédié `go1_mega`/`go1_gmax`, clé `nom|forme`) — **aucune cascade** vers `go1_pokedex_unique`, orthogonal au fait d'avoir "complété" l'espèce. Toujours triés par numéro national croissant.
- **Cascade automatique** (Pokédex/Shiny/les 6 modes forme unique, jamais Méga/Gmax) : cocher n'importe quelle forme (Pokédex/Shiny) ou n'importe lequel des 6 modes forme unique écrit réellement `go1_pokedex_unique[nat] = 1` (`go1CascadeToPokedexUnique`) — jamais grisé/"(auto)", une case normale. Cocher Shiny fait de même vers `go1_shiny_unique` (`go1CascadeToShinyUnique`). Si l'espèce n'a qu'une seule forme, la cascade redescend aussi vers la case "toutes formes" correspondante (`go1CascadeSingleForm`) — les deux vues représentent alors le même Pokémon. Jamais l'inverse (décocher ne déclenche rien).
- **Formes "Go attrapable"** (§4) : `go1AllFormsSorted` (source de Pokédex/Shiny/les 6 modes forme unique — jamais de Méga/Gmax, qui puisent dans `NAT_ALL_FORMS` en entier) inclut, en plus des formes réellement membres de `DATA.games["Go"]`, celles marquées `jeuVideoFor(...).goattrapable === true` seules (même logique que les formes dominantes Alola, `jeuOnlyFormsFor`, §5ter) — mémoïsées une fois au niveau module (`go1AttrapableOnlyForms`) pour ne jamais rebalayer tout le Pokédex à chaque espèce (coûteux en vue "Forme unique", un rebalayage par ligne affichée).
- **Fiche de capture** (clic sur un Pokémon) : `Go1SpeciesModal`. **"Disponible dans"** (`AvailabilityPills`, même composant/format que les autres marques, §5ter) tout en haut — Home / Go / Go sorti (§4, "Go" toujours entre Home et "Go sorti"). En dessous, les statuts en **pilules** (`TogglePill`, plus de case à cocher) : 4 lignes de 2 (Pokédex/Shiny, Chanceux/Parfait, Purifié/Obscur, XXS/XXL), toutes au niveau espèce ; puis, **si la forme précise cliquée porte le tag correspondant** (`formTagsFor`, jamais affiché sinon), les pilules Méga/Gmax — celles-ci au niveau de la **forme précise** (`nom|forme`), pas de l'espèce, et sans cascade.
- **Filtres** : Région, Sorti (Oui/Non, `goSortiFor`, comme l'onglet Go), Tous/Attrapé/Manquant (`StatusFilterPills`). Bouton **+** (barre flottante) : recherche et marque un Pokémon capturé dans le mode courant, ouvre sa fiche.

Ne filtre **pas** automatiquement sur Manquant au clic (retiré sur demande explicite). Repli d'affichage en cas d'échec de copie : champ texte sélectionnable.

## 5ter. Vues Jeu (Home vs "en jeu") — fermeture Banque Pokémon / fin transfert 3DS→Switch

Chantier motivé par la fermeture annoncée de la Banque Pokémon (plus de transfert 3DS→Switch) : permet de suivre, en plus de la possession sur Pokémon Home, la possession **dans une cartouche/jeu précis**, y compris pour des Pokémon jamais transférés sur Home. Vit entièrement **dans l'onglet Home de la marque concernée** (`GameView`) — pas un onglet séparé, contrairement à Go 1 (§5bis).

### Vues, entièrement modulables par l'utilisateur

- **`custom_jeu_views`** = `{ [marque]: [{ key, label, jeuKeys: [...] }, ...] }` — la liste réellement utilisée par l'app (hook `useJeuViews`). `DEFAULT_JEU_VIEWS` (const module-level) n'est qu'une **graine de migration one-shot** : si `custom_jeu_views[marque]` est absent au premier chargement pour une marque, elle est initialisée depuis `DEFAULT_JEU_VIEWS[marque]` (ou `[]`) puis persistée — `DEFAULT_JEU_VIEWS` n'est plus jamais relue après.
- **Créer une vue** : icône Pokédex de la barre du bas (menu "Mode") → ⚙️ → popup "Vues Jeu" → "+ Ajouter une vue" → **`JEU_VIEW_PRESETS`** propose ~17 paires/triples prédéfinies (Rouge/Bleu/Jaune, Or/Argent/Cristal, Or HeartGold/Argent SoulSilver, ... jusqu'à Écarlate/Violet, Rouge Feu Switch/Vert Feuille Switch, Vents/Vagues, Arceus, Z-A, Go) en un clic ; "Personnalisé…" ouvre la sélection manuelle jeu par jeu (`JEU_VIDEO_DEFS`, groupés par génération) si aucun préréglage ne convient. Modifier/supprimer une vue existante : même popup.
- Une vue peut regrouper 1 jeu (ex. Go) ou plusieurs (paire/triple partageant le même Pokédex, ex. Rubis/Saphir/Émeraude).

### Trois modes d'affichage (sélecteur "Mode", menu Pokédex de la barre du bas)

1. **Home** : lecture pure du flag `caught_<marque>` existant, strictement inchangée — ne lit/n'écrit jamais les données "en jeu" ci-dessous. Fiche de capture = `BoxGroupModal` (voir "Fiche de capture (jeux/marques)" ci-dessous pour la présentation actuelle).
2. **Home + jeu** : agrège Home et "en jeu". Coche **verte** si attrapé sur Home, **violette** si attrapé uniquement en jeu (`isSourcedOnly`). **Plus de badge "x/max" à droite de chaque ligne** (§ demande explicite — retiré : sur des marques comme Écarlate/Go/Arceus, ce chiffre ne signifiait rien de plus que la coche elle-même et différait d'un onglet à l'autre selon les vues configurées ; `pairStatsFor` reste défini mais n'est plus utilisé nulle part). Fiche de capture = `JeuMultiSourceModal` (même présentation que `BoxGroupModal`, voir ci-dessous) : case Home + une case par vue (toutes vues de la marque confondues), affichant le **nom réel du jeu/vue**, jamais un jeu individuel à l'intérieur d'une paire (la distinction fine, ex. Saphir Alpha vs Rubis Oméga, se fait via le Jeu-DO existant, pas par des cases séparées).
3. **Vue précise** (`PairModeBlock`, ex. "Saphir Alpha") : liste indépendante de Home (peut différer), filtrée par `DATA.jeuVideo` sur les clés de la vue (permissif tant que non renseigné, `jvAvailable`). Coche = attrapé dans **cette vue précise uniquement** (jamais Home — pas de case Home dans sa fiche). Reprend les mêmes filtres/boutons que Home (Statut, Région, Groupe de boîte, Jeu-DO, Liste/Boîte/Grille, réglages de boîte partagés avec la marque, recherche+ajout) sauf les coches "Afficher Shiny/Event", non pertinentes ici.

### Filtre "Disponibilité" (menu Filtres, marques avec vues configurées)

En plus des filtres habituels (Statut, Région, Groupe de boîte, Jeu-DO), un filtre **"Disponibilité"** liste : `Home` (appartenance à la marque, indépendante de `jeuVideo`) + un jeu précis par vue configurée (ex. X, Y, Saphir Alpha, Rubis Oméga pour VI) + toute **note de disponibilité conditionnelle** (texte libre, voir §4) trouvée sur l'un de ces jeux, toutes formes du Pokédex confondues (ex. "9G+") — n'apparaît que si au moins une fiche porte réellement cette note. Sélection multiple = union (au moins une correspond). Un jeu précis se teste avec `jvAvailable` (permissif, note texte = indisponible) ; une note se teste par égalité stricte à la note recherchée.

### Navigation dans le menu "Mode"

- En sélectionnant une marque **depuis le menu Home** (une marque différente de celle déjà affichée), le menu "Mode" s'ouvre automatiquement pour proposer directement le choix du jeu — le jeu précédemment ouvert pour cette marque reste néanmoins celui affiché par défaut (persisté par marque, `viMode`/`goSubView`, `useCachedState`). En revenant sur une marque depuis un **onglet non-marque** (National, Progression...), le menu ne s'ouvre pas tout seul.
- Cliquer "Go 1" (marque Go) ouvre lui aussi automatiquement, dans la foulée, la liste de ses sous-modes (Chanceux, Parfait...) — seul ce cas précis rouvre le menu ; toute sélection **finale** (un jeu précis, Go 2, Home, ou un sous-mode Go 1) referme le menu normalement, sans le rouvrir sur la vue suivante.
- Mécanique : `cameFromMarqueSwitch` (calculé dans `App`, comparaison avec l'onglet précédent) + `hasUserInteractedRef` (local à `GameView`, mis à `true` uniquement par le clic "Go 1") pilotent `autoOpenKey` de `FloatingActionBar` (ouverture au montage uniquement, une fois).

### Stockage "en jeu" (`game_tab_sources`)

`{ [marque]: { "nom|forme": [clé de vue, ...] } }` — clé = **clé de la vue** (`pair.key`), pas un jeu individuel : la distinction fine entre les jeux d'une même vue passe par le Jeu-DO existant, jamais par une case séparée (décision prise après une itération initiale trop fine, revenue en arrière). `useGameTabSources(marque)` : `setSource(key, jeuKey, on)` (coche rapide) et `setAllSources(key, jeuKeys[])` (remplacement complet, utilisé par la fiche détail qui connaît l'état final voulu de toutes les cases d'un coup).

### Pokémon "jeu seulement" (disponibles en jeu, absents de la marque)

Cas des formes dominantes Alola (attrapables dans les jeux Soleil/Lune mais non transférables sur Home) : un Pokémon peut être **structurellement absent** de `DATA.games[marque]` tout en étant explicitement marqué disponible dans un jeu précis (`jeuVideoFor(...)[clé] === true`, aucun défaut permissif ici — sinon quasi tout le Pokédex national apparaîtrait). `jeuOnlyFormsFor(marque, jeuKeys)` les retrouve (scan de `NAT_ALL_FORMS`) et les ajoute :
- **en fin de liste** (`extendedRows` = `[...rows, ...jeuOnlyFormsFor(...)]`), jamais interfolés — les positions 0..rows.length-1 restent celles de `DATA.games[marque]`, indispensable car `effective`/`flags`/`persist` (flag Home, positionnels) restent scopés sur `rows` original, jamais sur `extendedRows`. `useCollection`'s `persist()` reconstruit toujours depuis `DATA.games[key]` frais : un index synthétique au-delà de `rows.length` y est donc silencieusement ignoré, sans risque de corruption.
- dans la vue Home + jeu uniquement (`extendedRows`/`extendedSortOrder`/`extendedBoxInfo`, calculés en parallèle de `rows`/`sortOrder`/`boxInfo` bruts — la vue Home seule continue d'utiliser ces derniers, inchangés) et dans les vues précises concernées (`rowsForPair`, même logique).
- `toggle(i)` (coche rapide) détecte un index synthétique (`i >= rows.length`) et route alors vers `game_tab_sources` uniquement (jamais vers le flag Home, qui n'a pas de sens pour ces entrées).

### Fiche de capture (jeux/marques) — présentation actuelle

`BoxGroupModal` (Home, vue précise) et `JeuMultiSourceModal` (Home + jeu) partagent la même structure, fenêtre modale (`maxWidth: 420`, `maxHeight: 75vh`) — bouton fermer **×** dans la barre du bas, pas dans le panneau (§5septies) :

1. **Artwork** en haut, centré dans un cadre (`Sprite` taille 96) — même présentation que la fiche Catalogue (§3), à la place de l'ancien petit sprite (40px). National et Shiny reprennent désormais cette même présentation (§5septies). **Numéro** affiché en haut à gauche du cadre (`FicheArtworkBlock`, § demande explicite) : gras, plus gros, blanc, sans libellé "Numéro" ni "#" devant — et, sur ces deux fiches (`BoxGroupModal`/`JeuMultiSourceModal`), directement **éditable** dans le cadre lui-même (`input` transparent superposé, remplace l'ancien champ "No", voir point 4) sans qu'aucun indice visuel ne le signale. Affiche le **numéro dans le jeu/la marque** (`r[0]` de `DATA.games[marque]`, ou le numéro national en repli pour une entrée "jeu seulement" absente de la marque) — **jamais le numéro national**, qui reste réservé à la fiche National (seule fiche sans "jeu" précis auquel rattacher un numéro). **Badge Attrapé/Manquant** (§ demande explicite du 2026-09-02, "les fiches de capture n'indiquent pas si on a le pokémon et ne permettent pas de le rajouter") : en bas à droite du même cadre (props `caught`/`onToggleCaught` de `FicheArtworkBlock`, voir §5septies "En-tête harmonisé") — **cliquable** sur ces deux fiches (contrairement à National, §5octies, lecture seule car agrégée sur plusieurs marques). `BoxGroupModal` en vue précise : reflète/bascule `game_tab_sources[marque][key].includes(vue.key)`, écriture **immédiate** (même mécanisme que `toggleQuick` sur la coche rapide de la liste sous-jacente). `BoxGroupModal` en Home : reflète/bascule le flag Home lui-même (`displayEffective[i]`/`toggle(i)`), écriture immédiate aussi. `JeuMultiSourceModal` : reflète/bascule l'état local `home` — le **même état** que la pilule "Home" de la section "Attrapé dans" plus bas (point 5) — écrit seulement à l'**Enregistrer**, comme le reste de la fiche (`isDirty` en tient déjà compte).

### Numéro et groupe de boîte par vue

Un Pokémon peut avoir un **numéro** différent selon la vue (ex. X/Y range son Pokédex par emplacement dans Kalos, différent du rangement par défaut de la marque VI), et un **groupe de boîte** différent en **vue précise uniquement** — jamais en Home/Home + jeu pour le groupe de boîte, qui garde toujours celui de la marque. **Règle de tri commune** (Home, Home + jeu, vues précises) : d'abord par groupe de boîte (ordre défini dans Paramètres), puis par numéro en ignorant les lettres (`parseGameNumber`, ex. "E-415" → 415).

- **Numéro** (badge éditable en haut à gauche de l'artwork, § demande explicite — anciennement champ "No" séparé, voir "Fiche de capture (jeux/marques)" point 1/4 ci-dessus) : `game_view_number_overrides` = `{ [marque]: { [vueKey]: { "nom|forme": numero } } }`, hook `useGameViewNumberOverrides`. **Disponible dans les 3 modes** (Home, Home + jeu, vue précise, § demande explicite — avant : vue précise uniquement) : Home/Home + jeu utilisent une clé de vue dédiée `"__home__"` (jamais partagée avec les numéros de vue précise, pour ne jamais entrer en conflit). **Éditable uniquement au cas par cas depuis le badge de la fiche** — il n'existe aucune édition groupée en liste dans Paramètres (un bloc prévu pour ça avait été codé mais jamais réellement branché dans l'écran Paramètres ; supprimé comme code mort le 2026-09-01, voir §6, plutôt que réparé faute de besoin confirmé). **Utilisé pour le tri ET le nommage des boîtes en vue précise uniquement** : `computeGameSortOrder`/`computeGameBoxes` acceptent un paramètre optionnel `numberOverrides` (absent = comportement Home inchangé, numéro de la marque) — le numéro de la vue prime alors sur celui de la marque pour le rangement ET pour les bornes du libellé de boîte (ex. "Saphir Alpha 1-30"). **En Home/Home + jeu, le numéro `"__home__"` est pour l'instant seulement affiché/édité** — pas (encore) répercuté sur le tri ni le nommage des boîtes de ces vues. **Distinct du "Numéro spécifique par jeu vidéo"** (§4, `DATA.jeuVideoNumbers`) : ce dernier est une information de référence pure liée à la paire/triple de jeux (pas à une vue configurée par marque), n'affecte ni tri ni nommage de boîte, et c'est lui — pas `game_view_number_overrides` — qui alimente l'export Excel National (§7). `game_view_number_overrides` n'est **plus exporté** dans la feuille National depuis ce changement (reste piloté uniquement depuis le badge de la fiche, comme décrit ci-dessus).
- **Groupe de boîte** : `game_view_box_group_overrides`, même forme/hook analogue (`useGameViewBoxGroupOverrides`), **vue précise uniquement**. La **liste** des groupes possibles reste celle de la marque (`boxGroupOptions`, pas de liste séparée) — seule l'**affectation** par Pokémon peut différer. Fusionné **par-dessus** les overrides de la marque (`effectiveOverridesForPair = {...boxOverrides, ...boxGroupViewOverrides}`) avant d'être passé à `computeGameSortOrder`/`computeGameBoxes` : affecte donc aussi le **rangement réel** en vue Boîte de cette vue précise, sans aucune modification de ces fonctions partagées avec toutes les autres marques/vues. Pas de bloc Paramètres dédié pour l'instant (seulement l'édition au cas par cas depuis la fiche).

### Réglages de boîte par vue (lignes, colonnes, préfixe, grille)

Remplace l'ancien réglage unique par marque (`box_settings` = `{ [marque]: { size, prefix } }`, partagé sans distinction par Home/Home + jeu/toutes les vues précises) par un réglage **par vue** : `game_view_box_settings` = `{ [marque]: { [viewKey]: { rows, cols, prefix, gridCols } } }` (`viewKey` = `"__home__"`, `"__home_jeu__"`, ou la clé d'une vue précise) — hook `useGameViewBoxSettings(gameKey)`, une seule instance par `GameView`, sa fonction `getFor`/`save` transmise en props à `PairModeBlock` et à `JeuViewsSettingsModal` pour rester une source unique partagée (édition et affichage toujours synchro, jamais deux copies divergentes).

- **Capacité d'une boîte = `rows × cols`**, toujours cohérente avec l'affichage réel (`fixedRows`/`fixedCols` de `BoxGrid`) — corrige un défaut de l'ancien système où la capacité (`size`) était un nombre libre alors que `BoxGrid` affichait en réalité une grille **figée en dur à 5×6** : un `size` différent de 30 pouvait donc faire disparaître silencieusement des Pokémon de l'affichage (positions au-delà de la 5ᵉ ligne jamais rendues). `computeGameBoxes` accepte désormais un paramètre `cols` explicite (remplace le `6` en dur du calcul ligne/colonne).
- **Défauts** : 5 lignes × 6 colonnes (identique à l'ancien comportement figé, donc aucun changement visuel pour qui n'avait rien personnalisé), 6 Pokémon par ligne en vue Grille. Si `box_settings[marque]` existait déjà (réglage fait avant cette mise à jour), il sert de valeur de départ dérivée (`defaultBoxViewSettings`, cols=6, rows = ancien nombre par boîte arrondi au-dessus / 6) tant qu'aucune valeur n'a encore été enregistrée dans la nouvelle clé — rien n'est perdu.
- **Édition** : dans le bloc du jeu lui-même, jamais dans les Paramètres généraux (§ demande explicite) — bouton ⚙️ de la fenêtre "Vues Jeu" (icône Pokédex de la barre du bas → ⚙️, §5ter "Créer une vue"), qui liste désormais en plus, **en haut de la liste**, deux entrées fixes **Home** et **Home + Jeu** (non supprimables, seulement réglables) avant les vues précises configurées. Cliquer le crayon d'une entrée (fixe ou précise) affiche les champs lignes/colonnes/préfixe/grille **juste en dessous du nom de la vue** (pour une vue précise) ou seuls (pour Home/Home + Jeu, qui n'ont ni nom ni jeux à éditer) — composant partagé `BoxSettingsFields`. Pour une **vue tout juste créée**, ces champs n'apparaissent qu'au prochain crayon (clé pas encore connue au moment de la création, garde volontairement simple).
- **Stockage JSON uniquement** (`ALL_KEYS`, jamais de feuille Excel dédiée — comme l'ancien `box_settings`).

## 5sexies. Chaîne d'évolution

Fenêtre modale (`EvolutionChainModal`) ouverte en cliquant le libellé "Évolution : ..." (`EvolutionLabelButton`), présent dans National (fiche multi-formes), Home et les onglets jeu (`BoxGroupModal`, `JeuMultiSourceModal`). Reconstruit la lignée complète du Pokémon à partir de l'API publique PokeAPI, avec sprites/noms 100% locaux.

- **Résolution** (`resolveEvolutionChain`) : national → `pokemon-species` → `evolution-chain` (PokeAPI), puis arbre construit récursivement (`buildNativeEvolutionTree`). Résultat mis en cache en session, clé `"nat|regionTag"` (une région différente pour un même numéro national — ex. Miaouss Kanto vs Alola — doit reconstruire un arbre différent, jamais partager le cache).
- **Multi-évolution** : toutes les branches d'un embranchement sont affichées (Évoli → ses 8 évolutions, chacune avec sa propre flèche + méthode), sauf quand la région de départ en désigne une seule sans ambiguïté (`childrenToShow`) — Miaouss d'Alola n'affiche que Persian d'Alola, jamais Perrserker ni Persian Kanto.
- **Forme locale par défaut** (`pickLocalForm`) : préfère une forme "de base" reconnaissable (libellé contenant "non", ex. "Non Gmax", "Kanto non méga") quand aucune région ne correspond — évite qu'un Pokémon à nombreuses formes cosmétiques non régionales (ex. les casquettes de Pikachu) tombe au hasard sur l'une d'elles selon l'ordre du catalogue.
- **Méga-évolution / Gigantamax** : traités comme une évolution à part entière, pas une pastille à côté — détectés localement (absents de `/evolution-chain`) via `isMegaOrGmaxForme`, greffés comme enfants normaux de l'arbre natif avec flèche + méthode "Méga-évolution"/"Gigantamax", au même titre que n'importe quel autre lien (donc modifiables/masquables pareil, voir plus bas).
- **Nom en français** : `localForm.nom` si le Pokémon a une correspondance dans le catalogue local ; sinon repli sur `pokemon-species.names` (langue "fr") via `fetchFrenchSpeciesName`, ou le slug anglais mis en forme si l'appel échoue.
- **Édition manuelle** (bouton "Modifier", haut droit de la fenêtre) :
  - **"+ Évolution"** sous chaque Pokémon : ajoute un enfant, choix restreint aux membres de la même famille (`familyMembersOf`, repli sur la liste complète des noms si aucune famille n'est renseignée), puis forme, puis méthode libre.
  - **✎ sur chaque lien** (y compris Méga/Gmax) : modifier le texte de méthode, ou **masquer** le lien (natif) — réaffichable ensuite via la section "Liens masqués". Un lien **ajouté à la main** peut en plus y être **supprimé** directement (avec sa descendance ajoutée, retirée en cascade).
- **Stockage** : `evolution_chain_overrides` (§2), objet `{ [chainId]: { added: [{ key, nom, forme, parentKey, method }], linkOverrides: { "<parentKey>>>><childKey>": { method, hidden } } } }` — `chainId` = identifiant de chaîne PokeAPI (stable, indépendant du Pokémon utilisé pour ouvrir la fenêtre). Fusionné par-dessus l'arbre natif à l'affichage (`applyChainOverrides`), jamais persisté avec l'arbre lui-même (toujours re-résolu depuis PokeAPI + overrides).
- **Excel** : feuille dédiée "Chaînes évolution" (`buildChainesEvoSheetRows`/`importChainesEvoSheet`), colonnes `ChainId, Type (Ajout/Lien), ParentNom, ParentForme, Nom, Forme, Methode, Masque` — une chaîne entière (toutes ses lignes dans le fichier) remplace intégralement ses overrides existants à l'import, que le mode soit "add" ou "replace" (une chaîne est un tout cohérent, pas de fusion ligne à ligne).

## 5septies. Fiches National/Shiny en fenêtre modale + navigation entre fiches (National/Shiny/Home)

**Fiches National et Shiny** (§ demande explicite : "ressembler à celles de Home") : converties de page plein écran (`zIndex: 50`, fond uni) en **fenêtre modale** identique dans l'esprit à `BoxGroupModal`/`JeuMultiSourceModal` — fond assombri (`rgba(0,0,0,0.6)`, `zIndex: 100`), panneau centré (`PANEL2`, `maxHeight: 75vh`), artwork encadré 96px en haut. National affiche en plus, à côté de l'artwork principal, un second sprite shiny si une forme shiny existe pour l'espèce (même taille que l'artwork principal, 96px, sans étiquette — §5octies pour le détail des points où la présentation de National a depuis divergé de cette base commune : Forme/Évolution/Région dans l'en-tête, sélecteurs Vue/`cardMode`... le bouton Modifier et le bouton fermer, eux, ont depuis été réalignés sur le patron commun ci-dessous, voir "Barre du bas").

**Navigation entre fiches Pokémon différentes** (§ demande explicite), ajoutée dans les familles de fiches — National, Shiny, Double, Event, Interjeu, Home (les 3 modes : Home, Home + jeu, vue précise) — via trois moyens équivalents :
- **Clavier** ←/→ (ignoré si le focus est dans un champ de saisie) ;
- **Swipe tactile** horizontal (seuil 40px, ignore un mouvement trop vertical pour ne pas interférer avec le scroll normal de la page) ;
- **Flèches flottantes** ‹ › fixées en bas de l'écran (`FloatingCardNav`, `zIndex: 105`, `bottom: 92`). Prop optionnel **`center`** : contenu additionnel affiché entre les deux flèches, centré horizontalement par flexbox pleine largeur (`left: 0, right: 0, display: "flex", justifyContent: "center"`, jamais de `transform` — piège rencontré et corrigé, voir §6) — absent par défaut. Quand `center` est fourni, le composant reste monté même sans navigation possible (`hasPrev`/`hasNext` tous deux `false`) pour continuer à afficher ce contenu ; les flèches elles-mêmes restent conditionnées à une navigation réelle.

**Scroll de la liste sous-jacente bloqué tant qu'une fiche est ouverte** (§ demande explicite) : `useLockBodyScroll(active)` (hook module-level, défini juste après `useCardSwipeNav`) passe `document.body.style.overflow = "hidden"` tant que `active` est vrai, et restaure la valeur précédente à la fermeture (jamais `""` en dur, pour s'empiler correctement si une autre fenêtre modale était déjà ouverte en dessous). Appelé **indépendamment** de `useCardSwipeNav` dans les 7 fiches modales (National, Shiny, Double, Event, Interjeu, `BoxGroupModal`, `JeuMultiSourceModal`) — `useCardSwipeNav` ne s'active que s'il y a plusieurs éléments à parcourir, alors qu'une fiche seule, sans aucune navigation possible, doit quand même bloquer le scroll. Nécessaire car un overlay `position: fixed` seul n'empêche pas le scroll tactile du contenu sous-jacent sur Android/Chrome/Samsung Internet.

### Barre du bas — Modifier / + Capture / bascule Attrapé / Fermer / Enregistrer (National, Shiny, Event, Home/jeux, Catalogue)

Le groupe entier reste **centré horizontalement** dans la bande du bas (`FloatingCardNav`, jamais aligné à droite — un essai en ce sens a été fait puis annulé sur demande explicite : seul l'ordre interne au groupe importait, Enregistrer devant rester le dernier bouton du groupe, donc à droite des autres). Boutons ronds 46px, style partagé `GLASS_ROUND_BTN` (constante module-level, même look que les flèches — `GLASS_BG`/`GLASS_BLUR`/`GLASS_BORDER`/`GLASS_SHADOW`, `color: "#fff"`) :
- **Modifier** (`CatalogQuickEditButton`) : prop `style={GLASS_ROUND_BTN}`, jamais de prop `label` nulle part désormais (§3).
- **+ Capture** (Shiny uniquement, `addCatch`) : réutilise `GLASS_ROUND_BTN` avec un fond `GOLD`/`color: BG` par-dessus (couleur jaune conservée) — remplace l'ancien bouton "+ Capture" flottant séparé (`left: 50%, transform: translateX(-50%), bottom: 92, zIndex: 106`), qui n'existe plus. Aucune fiche jeux/Home n'a d'équivalent (pas de création de capture depuis ces fenêtres).
- **Bascule Attrapé** (`+`/`✓`, § demande explicite du 2026-09-02, "les fiches de capture n'indiquent pas si on a le pokémon et ne permettent pas de le rajouter" — Event, `BoxGroupModal`, `JeuMultiSourceModal`) : réutilise `GLASS_ROUND_BTN` avec un fond `OK` (vert, attrapé, symbole `✓`) ou `GOLD` (jaune, manquant, symbole `+`) par-dessus — permet aussi bien de marquer attrapé que de décocher. Bascule le **même statut** que le badge Attrapé/Manquant du cadre d'artwork (voir "En-tête harmonisé" ci-dessous et §5ter point 1 pour le détail par fiche : écriture immédiate sur `BoxGroupModal`, différée à l'Enregistrer sur `JeuMultiSourceModal`/état local `home`, via `updateCustom` sur Event). **Absent de Shiny** (`+ Capture` remplit déjà ce rôle) et de **National** (statut agrégé sur plusieurs marques, pas de bascule unique pertinente, §5octies) — voir aussi §5octies pour National, et la note de §6 pour l'exclusion volontaire de Double/Interjeu.
- **Fermer** (×) : `GLASS_ROUND_BTN` avec `fontSize: 20`. Sur `BoxGroupModal`/`JeuMultiSourceModal`, route vers `onCancel` (remplace l'ancien bouton "Annuler" du panneau, §5ter). Sur Shiny, route vers `closeEntry` (remplace l'ancien × en haut de fiche). ### En-tête harmonisé (artwork, numéro, nom, forme, évolution, Poképédia)

Trois composants partagés au niveau module (`FicheArtworkBlock`, `FicheNameRow`, `FicheFormeEvoRow`) portent l'en-tête de **toutes** les fiches détail ci-dessus (National, Shiny, Double, Event, Interjeu, `BoxGroupModal`, `JeuMultiSourceModal`) — même emplacement/format partout, pour que les futurs changements se fassent une seule fois :

- **Numéro** : en haut à gauche du cadre d'artwork (`FicheArtworkBlock`), gras, plus gros, blanc — plus de libellé "Numéro" ni de "#" devant (National affichait auparavant un "#" à côté du nom, retiré). Sur National/Shiny/Double/Event/Interjeu, affichage statique du numéro **national** (pas de "jeu" précis auquel le rattacher pour ces fiches). Sur `BoxGroupModal`/`JeuMultiSourceModal` (Home/Home + jeu/vues précises), le badge est en plus **directement éditable** (`input` transparent superposé) et affiche le numéro **dans le jeu/la marque**, jamais le national — voir "Fiche de capture (jeux/marques)" (§5ter) et "Numéro et groupe de boîte par vue" pour le détail.
- **Badge Attrapé/Manquant** (§ demande explicite du 2026-09-02, "les fiches de capture n'indiquent pas si on a le pokémon et ne permettent pas de le rajouter") : en bas à droite du même cadre — props `caught`/`onToggleCaught` de `FicheArtworkBlock` (`caught` absent/`null` = pas de badge affiché du tout ; sinon booléen, fond/texte vert `OK` si attrapé, orange `ACCENT` si manquant). Rendu en `<span>` (lecture seule) si `onToggleCaught` n'est pas fourni, en `<button>` cliquable sinon — **cliquable seulement quand le statut correspond à une bascule non ambiguë** : National (lecture seule, §5octies — le statut affiché agrège plusieurs jeux/marques déjà éditables individuellement plus bas dans la fiche), Shiny (lecture seule — `+ Capture` de la barre du bas fait déjà office de "marquer attrapé", pas de bascule simple possible avec plusieurs captures), Event/`BoxGroupModal`/`JeuMultiSourceModal` (cliquable — voir "Bascule Attrapé" ci-dessus et §5ter point 1 pour le détail par fiche). **Volontairement absent** de Double (chaque entrée du catalogue est déjà un exemplaire réellement possédé — pas de statut "manquant" pour ce genre de ligne) et d'Interjeu (fiche de transfert avant→après, pas un statut de possession pour un seul Pokémon) — voir §6.
- **Nom + Poképédia** (`FicheNameRow`) : nom à gauche, bouton Poképédia en pilule (bordure `ACCENT`) à droite, sur la même ligne — un slot `extra` optionnel affiche un contenu additionnel sous le nom (ex. compteur de captures sur Shiny).
- **Forme + Évolution** (`FicheFormeEvoRow`) : Forme à gauche ("Forme normale" si vide), Évolution à droite (`EvolutionLabelButton`) quand elle existe — sur la ligne suivante. Shiny n'avait pas de bouton Évolution avant cette harmonisation ; il en a désormais un comme les autres fiches (`EvolutionChainModal` ouvert/refermé via un state `showEvoChain` local, réinitialisé à chaque changement de fiche).
- **Interjeu** (transfert avec changement de Pokémon, "avant → après") : artwork et ligne Forme affichent les deux Pokémon reliés par une flèche (`→`) plutôt qu'un seul, cas particulier propre à cette fiche.

Puisque ce slot `center` doit maintenant être visible même sans navigation possible entre fiches (ex. un seul résultat filtré), `FloatingCardNav` est appelé **sans condition** dans toutes ces fiches (plus de `{hasNav && (<FloatingCardNav .../>)}`) — seuls `hasPrev`/`hasNext` restent conditionnés à une navigation réelle, le composant se chargeant déjà de masquer les flèches (pas le `center`) quand elles ne s'appliquent pas.

Mécanisme partagé : `useCardSwipeNav(active, onPrev, onNext)` (hook, clavier + swipe) et `FloatingCardNav` (flèches), tous deux déclarés au niveau module. **Distincte de la navigation existante "Précédent/Suivant" entre FORMES/CAPTURES d'un même Pokémon** (cardPos de National/Shiny) : celle-ci reste pilotée par clic uniquement (le clavier ←/→ a été réaffecté à cette nouvelle navigation, pour éviter toute ambiguïté entre les deux mécanismes). Chaque fiche calcule son propre index/liste de navigation à partir de la liste **actuellement affichée** (respecte donc le filtre/tri en cours) :
- **Shiny, Double, Event, Interjeu** : liste `filtered` de chaque onglet, clé `r.key` (ou équivalent local).
- **National** : `filteredForms` (mode "forms") ou `filteredSpecies` (mode "species"), selon le mode d'affichage actif.
- **Home / Home + jeu / vue précise** : liste `filtered` de `GameView`/`PairModeBlock`, appariée par `.i` (Home) ou par clé `nom|forme` (Home + jeu, vue précise).

`BoxGroupModal`/`JeuMultiSourceModal` reçoivent la navigation en props (`navIndex`, `navTotal`, `onNavPrev`, `onNavNext`, toutes optionnelles — absentes ou `navTotal <= 1` = pas de navigation affichée) et portent un `key={nom|forme}` côté appelant pour forcer un remontage complet à chaque changement de Pokémon (sinon les champs internes — groupe de boîte, Jeu-DO, numéro — resteraient ceux du Pokémon précédent, `useState(currentGroup)` ne se réinitialisant pas sur un simple changement de props).

**Espace réservé pour ne jamais chevaucher la fenêtre** (§ demande explicite, après un premier essai où le bouton "+ Capture" de Shiny se superposait à la flèche) : les 7 fenêtres concernées (`BoxGroupModal`, `JeuMultiSourceModal`, fiches National, Shiny, Double, Event, Interjeu) réservent `150px` de marge basse (`padding: "20px 20px 150px"` sur l'overlay) en plus du `maxHeight: 75vh`, pour que leur bord inférieur reste toujours au-dessus des flèches flottantes (`bottom: 92`). Le bouton "+ Capture" de Shiny fait désormais partie intégrante de la barre du bas (slot `center`, voir ci-dessus) plutôt que d'être positionné séparément — le risque de chevauchement qui a motivé cette marge ne se produit donc plus par construction pour ce bouton précis, la marge restant utile pour le reste du panneau.

- **`NumeroVueSection` (supprimée le 2026-09-01)** : fonction Paramètres codée pour l'édition groupée en liste des numéros par vue Jeu, jamais réellement appelée nulle part dans l'écran Paramètres — code mort depuis sa création, malgré une phrase d'aide (§5ter "Numéro et groupe de boîte par vue") qui en parlait comme si elle existait. Supprimée avec la phrase d'aide correspondante plutôt que branchée, faute de besoin confirmé (l'édition au cas par cas depuis la fiche de capture suffit). **Symptôme à surveiller pour repérer ce genre de cas à l'avenir** : une fonction top-level dont le nom n'apparaît **jamais** ailleurs dans le fichier (ni comme balise JSX `<NomDeFonction`, ni comme appel `NomDeFonction(`) est un candidat quasi certain au code mort.
- **Codes de jeu** (IàV, VI, Alola, GB, LG, Go, DEPS, Galar, LA, Paldea, LZA, GBA, VV — §5ter pour les 2 derniers) = clés internes de stockage (`caught_<code>`, `DATA.games`, etc.) — les renommer dans l'UI sans migrer toutes les clés casse les sauvegardes existantes.
- **`transform` sur un conteneur qui héberge du contenu arbitraire pouvant ouvrir une modale `position: fixed`** (piège rencontré et corrigé sur le slot `center` de `FloatingCardNav`, §5septies) : un `transform` sur un ancêtre crée un nouveau "containing block" pour tout descendant en `position: fixed` — une fenêtre modale ouverte depuis ce contenu (ex. `CatalogEntryModal` depuis le bouton Modifier de la barre du bas) se retrouve alors positionnée/redimensionnée relativement à ce petit conteneur au lieu du viewport entier (fiche minuscule et coupée), au lieu de centrer via `left: 50%, transform: translateX(-50%)`. Toujours centrer ce genre de conteneur par flexbox pleine largeur (`left: 0, right: 0, display: "flex", justifyContent: "center"`, jamais de `transform`), avec `pointerEvents: "none"` sur la bande pleine largeur et `"auto"` sur le contenu lui-même pour ne pas bloquer les clics de part et d'autre.
- **Pilule/case "Home" ≠ flag `jeuVideo`** (piège rencontré, §5ter) : la disponibilité sur Pokémon Home est l'appartenance à la marque elle-même (`DATA.games[marque]`, `patchMarqueMembership`), jamais un simple booléen `jeuVideo.home` — une première itération avait introduit ce raccourci à tort, revenue en arrière après clarification. **Trois notions "Home" distinctes à ne pas confondre** : (1) appartenance à la marque (ci-dessus), (2) `DATA.homeDex` = pilule "Pokédex Home" du catalogue (utilisée par National ET par l'onglet Home 2, §5quater — s'y tromper en utilisant `jeuVideoFor(...).home` a déjà vidé Home 2 alors que 1496 formes étaient cochées), (3) emplacement physique "Home 1"/"Home 2" (Interjeu/Double, champ `ou`/`catchLocation` — toujours comparer en égalité **stricte** à `DEFAULT_LOCATION`/"Home 2", jamais `/^Home/i` qui matche les deux à la fois, sauf regroupements volontairement larges comme la liste "autres emplacements"). Toujours vérifier laquelle des trois est concernée avant de toucher à ce code.
- **Familles "manquantes" (Home 2 §5quater, Go 1 Parfait §5bis, Go 2 §5quinquies)** : toujours vérifier par **forme** pour Home 2/Go 1 (une espèce à formes multiples, ex. Florizarre Non Gmax/Méga/Gmax, n'est "complète" que si toutes ses formes retenues sont cochées) — Go 2 est **par espèce** dès le départ (catalogue déjà agrégé), donc rien à agréger en plus côté "familles manquantes" pour cet onglet.
- **Positions `extendedRows`/entrées "jeu seulement" (§5ter)** : toujours ajoutées en **fin** de tableau, jamais interfolées — `effective`/`flags`/`persist` (flag Home) restent positionnels sur `rows` d'origine (`DATA.games[marque]`), un décalage casserait silencieusement le flag Home de tout le monde.
- **Alpha** : capacité "peut être Alpha" = colonnes `Alpha_LA`/`Alpha_LZA` de l'Excel source (`== 1` strict), pas les colonnes "déjà possédé en Alpha". Affichage limité au signe **α**, jamais le mot en toutes lettres.
- **Pseudo-jeu "Forme"** : pour les formes n'existant dans aucun jeu listé (Méga-évolutions...), coché manuellement, hors rattachement à un jeu précis.
- **Hooks React après un `return` conditionnel = écran noir.** Toujours déclarer `useState`/`useMemo`/`useEffect`/`useRef` avant le premier retour conditionnel du composant.
- **Listes de `Picker`/`MultiSelectFilter`** : toujours `orderedList(customXxx, découvertes)`, jamais `customXxx` seul (liste vide tant que l'utilisateur n'a rien ajouté manuellement, même si des valeurs existent déjà par capture).
- **Composants définis à l'intérieur d'un render** → remontés à chaque frappe → perte de focus clavier sur mobile. Toujours définir les composants au niveau module, données passées en props.
- **`transpileModule`** (validation JSX avant livraison) détecte les erreurs de syntaxe mais pas les `ReferenceError` runtime ni les variables redéclarées — compléter par une revue manuelle après tout refactor touchant les déclarations de state.
- **Clés stables `catalog_overrides`** : `"nom|forme"` d'origine (`row.__baseKey`), jamais positionnelles. Ajouts via `catalog_additions[].id` (`row.__additionId`), jamais mélangés avec `catalog_overrides`.
- **`RESET_KEEP_KEYS`** : `custom_marques` jamais supprimé lors d'un reset (casserait tous les dropdowns). Le "Réinitialiser tout" efface aussi `jeu_options_migrated` explicitement (hors `ALL_KEYS`) pour que la migration Jeu-DO se refasse après reset.
- **Zygarde** : formes `0.1`/`0.5` sont des nombres — toujours `String()` avant `.trim()`/`.toLowerCase()`.
- **z-index** : barre d'onglets à 30, `FloatingBackButton` à 55 (Double, toujours plein écran), fenêtres modales (Catalogue, fiches de capture, National/Shiny — §5septies) à 100, flèches flottantes de navigation entre fiches et slot `center` (Modifier/+ Capture/Fermer, §5septies "Barre du bas") à 105 (`FloatingCardNav`), blocs `ProgressStatsTable` sticky à 20 — ne jamais monter la barre d'onglets au-dessus de 100 (masquerait les fenêtres modales).
- **Champs contextuels par onglet** : ne pas ajouter un champ uniformément à tous les onglets si sa signification diffère selon le contexte (ex. Méthode/Détail sur Interjeu n'a de sens que dans le formulaire "+ Ajouter dans Shiny/Double", pas comme propriété permanente de l'entrée Interjeu).
- **Cache Android** : un fichier `.html` réouvert via `content://downloads/...` peut sembler "figé" sur une ancienne version — avant de chercher un bug de code, vérifier la donnée réellement embarquée dans le fichier livré.
- **`AvailabilityPills` sans prop `marque`** : la pilule "Home" fait alors `patchMarqueMembership(nom, forme, undefined, ...)` — ne plante pas, mais ne fait rien de visible (`DATA.gameIndex[undefined]` toujours vide). Toujours vérifier que les 3 sites d'appel (`BoxGroupModal` en vue Home et vue précise, `JeuMultiSourceModal`) transmettent bien `marque={gameKey}`.
- **`Picker` proche du bord droit de la fenêtre** (bouton en `justify-content: flex-end`, ou précédé d'autres champs sur la même ligne) : le panneau d'options par défaut (`left: 0`) peut déborder de la fenêtre. Passer `align="right"` dans ce cas (voir "Fiche de capture (jeux/marques)", §5ter) plutôt que de changer le comportement par défaut, qui reste correct pour tous les `Picker` alignés à gauche ailleurs dans l'app.
- **`isMegaOrGmaxForme` et le mot "non"** (§5sexies, piège sérieux déjà rencontré) : un simple `forme.includes("méga"/"gmax")` matche aussi le libellé de la forme **de base** de très nombreux Pokémon dans ce catalogue ("Non méga", "Non Gmax", "Non Gmax non méga", "Kanto non Gmax"...) — la forme de base disparaissait alors à tort de `localFormsForNat` (chaîne d'évolution tombant sur une variante cosmétique au hasard, ex. Pikachu affichant une casquette) et se retrouvait aussi proposée comme un faux Méga/Gmax à côté d'une autre forme du même nom. Toujours retirer les négations ("non méga"/"non gmax") avant de chercher le mot.
- **Pilules Méga/Gmax/Gmax gène (`formTagsFor`, §4) : ne jamais fusionner avec une détection automatique par texte de forme.** Une fusion avec `isMegaOrGmaxForme`/`dynamaxInfoFor` a été ajoutée puis retirée sur demande explicite — ces pilules doivent rester une valeur **que l'utilisateur ajoute lui-même**, jamais déduite. Ne pas réintroduire ce genre de repli sans demande explicite, même pour "corriger" un Pokémon visiblement Gmax/Méga mais non encore tagué.
- **`navigator.clipboard.writeText`** échoue silencieusement (ou est absente) dans certains contextes mobiles (webview Samsung Internet non sécurisé, focus, permissions refusées) — toujours passer par `copyToClipboard(str)` (repli `textarea` + `document.execCommand("copy")`), jamais l'API clipboard directement.
- **`natInfoFor(nom, null)`** (recherche par nom sans forme) échoue et retombe sur `n: 999999` si cette espèce n'a jamais de forme "vide" dans le catalogue (ex. Floette) — pour un nom seul (ex. famille d'évolution via `familyMembersOf`), toujours prévoir un repli via `NAT_ALL_FORMS.find(f => f.nom === nom)`.
- **`window.storage.get(key)` ne lève plus d'exception pour une clé absente** (corrigé — levait `throw new Error("not found")` auparavant). Piège très largement répandu dans le fichier : tout bloc "lire l'existant → modifier → réécrire" placé dans le **même `try`** voyait son `set()` final silencieusement annulé par le `catch` englobant, dès la toute première utilisation d'une nouvelle clé de stockage (ex. `game_view_box_group_overrides`, jamais écrite avant le tout premier import Excel avec des groupes de boîte par vue — les numéros fonctionnaient déjà car cette clé-là avait déjà été écrite une fois). Confirmé en extrayant la fonction réelle du fichier et en la faisant tourner contre un export Excel réel (0/540 avant correctif, 540/540 après). Toujours garder cette hypothèse en tête si un `set()` semble "ne rien faire" sans erreur visible.
- **Capacité de boîte figée en dur** (piège rencontré, corrigé — voir "Réglages de boîte par vue", §5ter) : avant l'introduction de `game_view_box_settings`, `BoxGrid` affichait toujours une grille **5×6 figée en dur** (`fixedRows={5} fixedCols={6}`) alors que le réglage `box_settings.size` (nombre par boîte) était un champ libre — un `size` différent de 30 faisait donc disparaître silencieusement des Pokémon de l'affichage (positions au-delà de la 5ᵉ ligne jamais rendues), sans aucune erreur. Toujours garder `fixedRows`/`fixedCols` de `BoxGrid` et la capacité réelle (`rows × cols`) strictement dérivés de la même source pour ce genre de réglage — jamais un nombre libre d'un côté et une grille figée de l'autre.
- **Numéro national ≠ numéro dans le jeu/la marque** (§5ter, §5septies) : `natInfoFor(nom, forme).n` est le numéro **national** (Pokédex national, utilisé par National/Shiny/Double/Event/Interjeu) ; `DATA.games[marque][i][0]` (souvent noté `r[0]`) est le numéro **dans cette marque précise**, peut différer du national (ex. Pokédex régional). Le badge numéro des fiches jeux/Home (`BoxGroupModal`/`JeuMultiSourceModal`) affiche et édite **toujours** ce second numéro (avec surcharge par vue, `game_view_number_overrides`) — ne jamais le confondre avec `natInfoFor(...).n`, qui n'a de sens que sur les fiches sans "jeu" précis (National notamment).
- **`spriteCandidates` retombait silencieusement sur le mauvais Pokémon** (piège rencontré et corrigé — ex. Rattata d'Alola bien affiché dans la marque Alola mais pas en National) : une forme régionale/cosmétique sans identifiant numérique dédié (`REGIONAL_SPRITE_IDS`/`MEGA_GMAX_SPRITE_IDS`, absent pour la plupart des formes régionales) n'a souvent **pas** d'artwork officiel disponible sous le nom suffixé (`<num><suffixe>.png`) — l'ancien ordre de repli retombait alors directement sur l'artwork de la forme de **base** (espèce par défaut, souvent Kanto/Non Gmax), sans jamais tenter le sprite pixelisé suffixé (`SPRITE_BASE` + suffixe), qui lui fonctionne de façon fiable pour ces formes. Résultat : mauvais Pokémon affiché en grand format sans aucune erreur visible ni image cassée — se voit surtout sur l'artwork 96px des fiches, passait inaperçu sur les listes en 32px pixelisées (chemin déjà correct). Le composant `Sprite` étant partagé par tous les onglets, le correctif (épuiser artwork dédié → artwork suffixé → pixel dédié → pixel suffixé, avant seulement de retomber sur la forme de base) s'applique uniformément à National et aux onglets jeu.
- **`buildFullCatalogOverrides()`** (utilisée par l'export JSON *et* la synchro Gist, voir §7/§8) reconstruit une version "complète" du catalogue qui **remplace entièrement** — jamais fusionne — la valeur lue en stockage juste avant dans `buildExportOut`. Tout champ absent de cette reconstruction disparaît donc silencieusement de chaque export/synchro, même s'il est bien présent en stockage local. A déjà oublié `jeuVideo` une fois (corrigé) — vérifier cette fonction en premier si une donnée du catalogue "ne survit pas" à un export/import ou à une synchro Gist alors qu'elle persiste correctement en local.
- **`ts.transpileModule` ne détecte PAS un `const`/`let` redéclaré deux fois dans la même portée** (constaté : deux `const prevTabRef` dans `App`, validation `ts.transpileModule` passée sans erreur, mais Babel — le moteur réellement utilisé par le navigateur via `<script type="text/babel">` — refusait de transpiler, écran noir total dès l'ouverture, avant toute interaction). `ts.transpileModule` reste utile pour la JSX/syntaxe générale mais **ne suffit pas** à garantir qu'un fichier chargera réellement dans le navigateur. Avant toute livraison touchant les déclarations de state/refs d'un composant déjà volumineux (`App`, `GameView`...), valider **aussi** avec `@babel/standalone` en runtime `"classic"` (celui utilisé par le navigateur, pas `"automatic"` — qui injecte des `import` ESM absents du contexte réel et fausserait le test) : `Babel.transform(code, { presets: [["react", { runtime: "classic" }]] })`. Un `grep -c "const <nom>"` ciblé sur le nom d'une variable nouvellement introduite est aussi un filet de sécurité rapide.
- **Formulaire dupliqué entre deux onglets** (§5octies, "Ajouter un shiny" National vs édition Shiny) : dès que Yann demande explicitement qu'une saisie reste identique et synchronisée entre deux endroits, extraire un composant module-level partagé (`ShinyRecordFields`) plutôt que copier le JSX — la duplication se dé-synchronise silencieusement au premier futur changement fait d'un seul côté. Le composant partagé ne couvre que la saisie commune ; les actions spécifiques à un contexte (ex. Suppression/Interjeu, valables seulement sur une capture déjà persistée) restent dans le JSX de l'appelant, jamais dans le composant partagé.
- **Style d'un composant partagé à adapter à plusieurs sites d'appel** (bouton Modifier stylé comme les flèches, §5septies "Barre du bas") : ajouter un prop `style` optionnel fusionné **par-dessus** le style par défaut (`{...defaultStyle, ...(style || {})}`), jamais changer le style par défaut lui-même. `CatalogQuickEditButton` n'a par ailleurs plus aucun appelant utilisant son style par défaut (les 4 sites d'appel passent tous désormais `style={GLASS_ROUND_BTN}`) ni sa prop `label` — garder ce filet malgré tout pour tout futur nouvel appelant qui voudrait un style différent.

## 7. Export/Import Excel (bouton "Excel" de l'en-tête)

Un onglet cochable = une feuille du classeur `Pokédex export.xlsx` (SheetJS). Nom+Forme toujours en 2 premières colonnes, Forme vide affichée `-`, dates en vraies cellules Excel `dd/mm/yyyy` (`excelDateCell`/`excelParseDateFR`, construites en UTC pour éviter un décalage d'un jour).

- **National** : feuille unique, **fusion de l'ancienne "National" et de l'ancienne "Paramètres"** (§ demande explicite — mêmes ~1600 lignes, colonnes différentes). Ordre des colonnes : d'abord **Paramètres** (catalogue éditable) — `Nom, Forme, Numero, Region, Evolution`, `AlphaLA`/`AlphaLZA`, `HomeDex`, `FormMega`/`FormGmax`/`FormGmaxGene` (pilules Méga/Gmax/Gmax gène, §4 — valeur stockée uniquement, jamais déduite du texte de forme), une colonne par jeu (`GAME_ORDER`, numéro exact dans ce jeu, éditable — jeu de colonnes complet requis pour être pris en compte, par sécurité) — puis **National** — une colonne **`Dispo_<jeu>`** par jeu (disponibilité structurelle 1/0, **pas** le statut attrapé, qui vit dans les feuilles de jeu/LA/LZA ; renommée depuis l'ancien nom de colonne nu pour ne pas entrer en collision avec le numéro par jeu ci-dessus), `Forme(manuel)` (pseudo-jeu "Forme", éditable), puis le **bloc "Jeu vidéo"** (§ demande explicite de réorganisation — remplace l'ancien double bloc plat `JV_<clé>` (tous les jeux à la suite) + `NumeroVue_<jeu>_<vue>` (dépendait de `custom_jeu_views`, donc absent tant qu'aucune vue n'était configurée pour la marque, et coupait un triplé en deux si une vue ne couvrait que 2 des 3 jeux) : un groupe de colonnes par entrée `JEU_VIDEO_PAIRS` (§4, personnalisable, déjà dans l'ordre d'affichage "1G → 10G"), de gauche à droite : **`No_<ACRONYME>`** (numéro spécifique du groupe, depuis `DATA.jeuVideoNumbers` — §4 "Numéro spécifique par jeu vidéo", **indépendant** de `custom_jeu_views`, donc toujours présent), **`JV_<clé1>[, JV_<clé2>, JV_<clé3>]`** (disponibilité, une par jeu du groupe — `0`/`1` classiques ou **texte libre**, note de disponibilité conditionnelle, §4 — `JV_go` relit aussi l'ancienne colonne `GoSorti`), puis une **colonne vide** de séparation avant le groupe suivant. L'acronyme vit directement sur le groupe (`JEU_VIDEO_PAIRS[].acronym`, éditable dans Paramètres → "Jeu vidéo", §4) — une colonne dont l'acronyme ne correspond plus à aucun groupe actuel (groupe renommé/supprimé depuis l'export) est silencieusement ignorée à l'import, comme une colonne absente. Coloration des en-têtes par groupe (demandée) : **non réalisable** avec la bibliothèque SheetJS gratuite chargée ici (`xlsx.full.min.js`) — l'écriture de styles de cellule est réservée à la version payante "Pro" ; le regroupement + colonnes vides reste le seul repère visuel. Les anciennes colonnes `NumeroVue_<jeu>_<vue>` ne sont plus reconnues à l'import (transition volontairement sans historique, § demande explicite — JSON conservé par ailleurs). `AlphaLA`/`AlphaLZA` et `Dispo_<jeu>` : informatifs, ignorés à l'import (disponibilité modifiable uniquement via le Catalogue, §21bis) ; toutes les autres colonnes fusionnées à l'import (jamais de suppression de fiche via cette feuille). Une ancienne feuille "Paramètres" séparée reste importable isolément (compatibilité descendante avec les fichiers exportés avant la fusion), mais n'est plus générée à l'export.
- **Jeu vidéo** (§4) : une ligne par jeu vidéo (`JEU_VIDEO_DEFS`), colonnes `Cle, Nom, Generation, Marques` (liste séparée par `, `), `Groupe` (= l'acronyme du groupe `JEU_VIDEO_PAIRS` auquel ce jeu appartient — les jeux qui partagent la même valeur dans cette colonne forment un même groupe à numéro partagé, pas de colonne Acronyme séparée). `buildJeuVideoSheetRows`/`importJeuVideoSheet` : une ligne avec `Cle` reconnue met à jour Nom/Generation/Marques/regroupement du jeu correspondant ; une ligne sans `Cle` (ou inconnue) crée un nouveau jeu (clé générée depuis `Nom`, même mécanisme que "+ Ajouter un jeu" en Paramètres). Jamais de suppression de jeu via cette feuille.
- **Générations JV** (§4) : un bloc de génération par ligne (`Generation`), dans l'ordre d'affichage — feuille séparée de "Jeu vidéo" ci-dessus pour qu'un bloc encore vide (aucun jeu dedans) ne disparaisse pas de l'export faute de ligne à laquelle s'accrocher. `buildJeuVideoGensSheetRows`/`importJeuVideoGensSheet` : mode "replace" = la liste devient exactement celle du fichier (permet de retirer un bloc) ; mode "add" = les blocs du fichier s'ajoutent à la suite de ceux déjà existants, rien n'est retiré.
- **Shiny** : catalogue dédupliqué + doublons, colonnes `Nom, Forme, Attrape, Marque, Mode, Detail, Date, Jeu, Gmax, Alpha, NomBoite` (Attrape fusionné avec l'emplacement).
- **Double** : une ligne par capture réelle (pas de dédup), colonnes `Nom, Forme, Attrape, Marque, Mode, Detail, Date, Shiny, Jeu, Alpha, Gmax, FromInterjeu`.
- **Event, Interjeu** : catalogues éditables complets, y compris `DOPersonnel`/`JeuDO` (Event) et `FromInterjeu` (lien Shiny/Double, JSON sérialisé en texte).
- **Listes, Jeu par marque, Groupe de boîte, Disponibilité** : couverture exhaustive des listes personnalisées (Marque/Méthode/Détail/Emplacement, `custom_jeux`, `custom_box_groups`, `mode_marques`/`detail_marques`) — répliquent le calcul `orderedList(custom, discovered)`, sinon des valeurs "découvertes seulement" disparaissent silencieusement de l'export.
- **Home 2** (§5quater) : une ligne par forme marquée "Pokédex Home" (`DATA.homeDex`, même catalogue que l'onglet — ne diverge jamais), colonnes `Nom, Forme, Attrape`.
- **Go 2** (§5quinquies) : une ligne par **espèce** (`speciesRepresentatives()`, toutes, y compris exclues), colonnes `Nom, Forme, Attrape, Exclu`. La colonne Forme d'une ligne importée est ignorée pour la clé de stockage si elle ne correspond pas à la forme représentative actuelle de l'espèce — seul le Nom fait foi, robuste même si le fichier a été généré avec une version antérieure du catalogue.
- **Vues Jeu** (§5ter) : une ligne par vue (`Marque, Nom, Jeux` — jeux séparés par `, `, labels `JEU_VIDEO_DEFS`), `buildJeuVuesSheetRows`/`importJeuVuesSheet`. Ne couvre que les **définitions** des vues (nom + jeux qui la composent) ; à l'import, une vue reconnue (même Marque + même Nom) garde sa clé interne pour ne pas perdre les données déjà cochées sous cette vue.
- **Chaînes évolution** (§5sexies) : ajouts manuels + overrides de lien de `evolution_chain_overrides`, colonnes `ChainId, Type (Ajout/Lien), ParentNom, ParentForme, Nom, Forme, Methode, Masque` — voir §5sexies pour le détail du format et de la fusion à l'import.
- **Onglets par jeu** : une feuille par jeu (dynamique, dérivée de `GAME_ORDER` — inclut donc GBA/VV automatiquement), structure standard capture/possession, plus (§5ter, marques avec vues configurées) deux blocs de colonnes dynamiques, une occurrence par vue de la marque : **`EnJeu_<clé de vue>`** (1/0, attrapé dans cette vue), **`GroupeVue_<clé de vue>`** (groupe de boîte spécifique, vide = groupe de la marque). Absence d'une colonne dans le fichier importé = donnée non touchée (jamais écrasée silencieusement), y compris pour les vues/jeux non couverts par le fichier. Le numéro spécifique par vue (`game_view_number_overrides`, §5ter — **distinct** du "Numéro spécifique par jeu vidéo" exporté en National, §4) n'a jamais eu de colonne dans cet onglet lui-même ; une ancienne colonne `NumeroVue_<clé de vue>` provenant d'un très ancien fichier (avant la centralisation dans la feuille National) reste lue en compatibilité descendante mais n'est plus générée à l'export. **Go 1** (§5bis) : feuille dédiée, voir détail plus haut.

## 9. Workflow de livraison

1. Éditer `/mnt/project/index.html` directement (`str_replace`, contexte suffisant pour un match unique).
2. Extraire le bloc `<script type="text/babel" data-presets="react">` (ancre non-ambiguë — ne jamais chercher juste `<script type="text/babel"` seul, ça matche aussi du texte dans certains commentaires), valider via `ts.transpileModule` (JSX React preset, `/home/claude/.npm-global/lib/node_modules/typescript`). Le bloc `window.DATA` (§1) n'a pas besoin d'être extrait ni validé à part — c'est du JSON pur, jamais de JSX dedans.
2bis. Pour toute modification touchant les déclarations de state/refs d'un composant volumineux (`App`, `GameView`...), valider **en plus** avec `@babel/standalone` en runtime `"classic"` (§6 — `ts.transpileModule` seul ne détecte pas un `const` redéclaré deux fois dans la même portée, cause déjà avérée d'écran noir total).
3. Si `DATA` lui-même est modifié (ajout d'un jeu) : après édition, revalider que `window.DATA = {...};` reste un JSON strictement valide (ex. `json.JSONDecoder().raw_decode` en Python sur le texte après `window.DATA = `) avant de toucher au reste — une virgule ou guillemet mal fermé y casse silencieusement tout le chargement.
3bis. **Réflexe harmonisation/zéro code mort (§ priorité permanente, voir note en tête de document)**, sur la zone touchée par la modification et son voisinage direct : si la modification introduit une fonction/un style/un composant, vérifier par `grep` qu'un équivalent n'existe pas déjà ailleurs dans le fichier avant d'en écrire un nouveau ; si elle rend une fonction/un état existant obsolète, le supprimer plutôt que le laisser en place "au cas où" (sauf filet de compatibilité explicitement voulu, ex. lecture d'une ancienne clé de stockage pour migration). Un `grep -c "NomDeLaFonction"` égal à 1 (seulement la déclaration) signale un candidat au code mort. Ne pas étendre ce réflexe à une relecture systématique de tout le fichier à chaque livraison — seulement la zone concernée par la demande en cours ; une passe plus large reste une demande explicite séparée (comme celle du 2026-09-01, §6).
4. Mettre à jour `APP_VERSION` (`année.mois.jour.heure(24h).minute`, heure réelle de génération).
5. Copier vers `/mnt/user-data/outputs/index.html`, `present_files`.
6. Nommer systématiquement `index.html` (jamais `Pokédex.html`).
7. Ne jamais proposer de mettre à jour cette documentation après une modification — uniquement si demandé explicitement.
